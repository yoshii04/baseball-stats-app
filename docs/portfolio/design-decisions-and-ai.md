# 設計判断と AI の使い方

3 本の個人開発（[紹介ページ](README.md)）は、AI（Claude Code）と一緒に進めています。このページは、**AI と人の役割分担と、その進め方**をまとめたものです。

## 役割分担

| | 担当 |
|---|---|
| **AI** | 内容の検討・作成（ADR・仕様書・テスト・実装・レビュー修正の下書きと作業） |
| **人** | AI の成果物の**レビュー、方向性の確認、修正、承認** |

- やる／やらないの判断と、ADR の承認は人が行います。
- AI の出力は、テスト・CI・別の観点での AI レビューで検証したうえで、人がレビューして承認します。
- 当時の動機が記録に残っていないものは、AI に推測で書かせず「記録なし」と明記し、人が追記します。

## 進め方

機能を足すときは、1 機能ごとに PR を分けて、次の順で進めます（同じ手順を、householdAccountBook の README と performanceRecords の CLAUDE.md にも書いています。どちらも非公開です）。

| 段階 | 内容 | AI | 人 |
|---|---|---|---|
| 1. ADR | なぜ変えるか、選択肢、決定、見送る理由 | 検討して下書きを作る | レビューし、方向性を確認して、承認する（ステータスを変える） |
| 2. 仕様書 | 何を変えるか（画面・API・入出力） | 検討して下書きを作る | 内容を確認・修正し、ADR とセットでマージする |
| 3. テスト（Red） | 仕様どおりに動くことを確かめるテストを、**実装より先に**書く | 作成する | レビューする |
| 4. 実装（Green） | テストが通る最小の実装 | 作成する | レビューする |
| 5. レビュー | 観点を変えて AI にレビューさせ、指摘を修正する。CI はリポジトリにより `pytest`・`pip-audit`・`ruff`・`vitest` | 指摘と修正案を作る | 指摘への対応方針を確認し、修正を承認して、マージする |
