# ADR-0005: AWS 上の常時公開を止め、ローカル利用と必要時の起動にする

- ステータス: 採用済み（遡及記録）
- 決定時期: 2026-10-12 時点で停止中。実際に停止した日は記録なし
- 関連: [ADR-0003](0003-google-oauth-allowed-emails.md)、[AWS 手順](../aws-deploy.md)、[公開対応 改修計画](../plan/public_release_plan.md)

> 停止の理由として記録が残っているのは「費用の関係」（所有者の申告）だけである。
> 選択肢と金額は `docs/plan/public_release_plan.md` の見積もりを引用したもので、**実際の請求額は未確認**。
> 停止した時点の利用状況（利用者数・アクセス数）は記録なし。

## 背景

- 学習目的で、EC2（PostgreSQL と FastAPI を Docker Compose で起動）+ Nginx + S3 + CloudFront に公開する構成を作り、
  GitHub Actions から EC2 へデプロイできるようにした（[ADR-0003](0003-google-oauth-allowed-emails.md) の認証付き）。
- 利用者はチーム内の少数（計画書の前提は 20 名以下）で、成績の登録は CLI、閲覧は Web 画面で行う。
- 常時起動すると、利用の有無にかかわらず EC2 と EBS の費用がかかる。
- `main` への push のたびに deploy ジョブが走る設定だったため、EC2 を止めると CI が失敗し続けた。

## 選択肢

月額は `public_release_plan.md` の見積もり（東京リージョン、EC2 のみ構成。$1 = 150 円換算の記載あり）。
停止中も EBS の課金が続く点は、同ファイルの注記による。

| 選択肢 | 月額の目安 | 利点 | 欠点 |
|---|---|---|---|
| A. 常時起動（EC2 を止めない） | EC2 $7.75 + EBS 約 $2〜3（無料枠終了後） | いつでも画面を見られる | 使わない時間にも課金される。攻撃面が常時ある |
| B. 必要なときだけ起動（1 日 2 時間想定） | 約 $3.62（EC2 $0.70 + EBS $2.88） | 費用を抑えつつ、構成はそのまま | 起動・停止・データ登録の手間がある。EBS 分は停止中も課金 |
| C. 休眠（EC2 を止めたまま） | EBS 分のみ（30GB で約 $2.88） | 再開できる状態を保てる | 使えない。費用はゼロにならない |
| D. 完全に削除 | $0 | 費用も攻撃面もなくなる | データと環境の再構築が必要。再開の手間が最大 |
| E. ローカルのみ | $0 | 費用なし。実データを外に置かない | 他のメンバーが見られない |

## 決定

**AWS 上の常時公開を止める。** 利用はローカルを基本とし、他のメンバーに見せる必要があるときだけ EC2 を起動する（選択肢 B・C の運用）。

1. EC2 は停止状態で保持する。EBS は残し、再開に必要な構成を保つ。
2. GitHub Actions の deploy は `workflow_dispatch`（手動実行）に変更した。`main` への push ではテストだけが走る。
3. 再開手順は [AWS 手順](../aws-deploy.md)（STEP 1〜7）に残す。
4. 画面の確認は、合成データのデモ（[demo/README.md](../../demo/README.md)）で代替できる。

## 理由

- 利用の頻度に対して、常時起動の固定費が見合わなかった（所有者の判断。数値の裏付けは上記の見積もり）。
- 構成を残して止めるだけなら、再開の手間が小さい。削除（選択肢 D）は再構築の手間に見合う節約にならない。
- テストの自動実行と EC2 へのデプロイを分けることで、停止中も CI を緑に保てる。

## 結果

- 良い点: 固定費を EBS 分に抑えられる。CI は緑のまま運用できる。
- 悪い点: 他のメンバーが見るたびに、起動・データ登録・停止の手作業が発生する。
- 停止中も EBS（約 $2.88/月の見積もり）は課金される。完全に $0 にするには終了（削除）が必要で、その場合は再構築になる。

## 再開手順

[AWS 手順](../aws-deploy.md) のとおり。要約は次のとおり。

| 手順 | 内容 | 場所 |
|---|---|---|
| 1 | EC2 を起動する（`aws ec2 start-instances`） | AWS |
| 2 | SSH 接続し、`docker compose ps` で `db` と `backend` の起動を確認する | EC2 |
| 3 | 記録の Excel を転送し、`config.json` のパスを確認する | ローカル → EC2 |
| 4 | `python import_db.py` でデータを登録する | EC2 |
| 5 | `curl localhost:8000/api/stats/season` で確認する | EC2 |
| 6 | 作業が終わったら EC2 を停止する（`aws ec2 stop-instances`） | AWS |

### 手順書の未整備な点

- S3 + CloudFront へのフロントエンド配信の手順は、リポジトリ内に文書化されていない（EC2 側の手順だけがある）。
  再開時にフロントエンドも更新する場合は、手順を確認して追記する。
- 再開後の Elastic IP・ドメイン・Google OAuth の許可オリジンが、停止前のままであることの確認手順がない。

## 見直しの合図

- 利用者が増え、常時の閲覧が必要になった（選択肢 A に戻す）。
- 実際の請求額が見積もりと大きく異なることが分かった。
- フロントエンドを静的デモとして外部に置く必要が出た（費用は無料枠の範囲で足りる見込み。条件は公式ページで確認する）。
