# ADR-0004: DB マイグレーション（Alembic）の導入を見送る

- ステータス: **提案（要承認）**。承認後に「採用済み」へ変更し、日付を入れる
- 関連: [ADR-0002](0002-plain-sql-without-orm.md)

> この ADR は、現状の事実から導いた推奨案です。決めるのはリポジトリの所有者です。
> 異なる判断をする場合は、決定・理由・結果を書き換えてください。

## 背景

- スキーマは `docker/init.sql` に集約している。コンテナの初回起動時に自動実行される。
- スキーマを変更するときは `init.sql` を編集し、`docker compose down -v` で DB を全消去してから、
  `import_db.py` で Excel から再登録している。
- 過去の個別マイグレーション SQL は `init.sql` に統合済みで、`tmp/sql/` は履歴としてのみ残っている
  （`migrate.py` は `tmp/sql/NNN_*.sql` を順に適用する簡易ランナー）。
- `CLAUDE.md` の「将来の改善予定」に Alembic が挙がっている。

## 決定（案）

**現時点では Alembic を導入しない。** 次のいずれかが起きた時点で導入する。

1. DB 上にしか存在しないデータ（Excel から再生成できないもの）を持つようになる。
2. 本番 DB を止めずにスキーマを変更する必要が出る。
3. 複数人が別々の環境のスキーマを同期する必要が出る。

## 理由

- 現在のテーブルの内容はすべて Excel（入力元）から `run_all.py` / `import_db.py` で再生成できる。
  全消去 → 再登録が許容できるので、スキーマの差分適用の仕組みが無くても運用できる。
- Alembic はモデル定義（SQLAlchemy）と組み合わせると効果が大きい。
  ORM を使わない方針（[ADR-0002](0002-plain-sql-without-orm.md)）のまま導入すると、
  手書きのマイグレーションを管理する手間だけが増える。
- DB に書き込むのは `import_db.py` だけで、実行するのは Excel を管理する運用者である（Web API は GET のみ）。
  環境は「ローカル」と「EC2」の 2 つだけである。

## 結果

- 良い点: 仕組みが増えず、`init.sql` 1 ファイルでスキーマ全体が読める。
- 悪い点: 本番 DB の変更は全消去と再登録になる。EC2 では停止・再登録の手間がかかる。
- 見直しの合図は上の 1〜3。見直す場合は SQLAlchemy への移行（`docs/plan/public_release_plan.md` STEP 3）と
  合わせて判断する。
