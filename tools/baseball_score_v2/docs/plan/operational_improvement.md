# 運用面向上のための機能追加 STEP 案

## Context

現状の baseball_score_v2 は機能面の開発がほぼ完成した。
今後は「毎試合後にデータを登録・確認する運用」をよりスムーズにすることを目的として、
運用面の改善を段階的に進める。

---

## 現在の運用ワークフロー（課題の背景）

```
試合後
  ↓ (1) Excelに打撃・投手データを手入力
  ↓ (2) python generate.py       — 集計表示・試合入力ファイル生成
  ↓ (3) python import_db.py      — DB登録
  ↓ (4) python write_score.py    — Excelにスコア書き込み（任意）
  ↓ (5) python analytics.py      — 分析Excel出力（任意）
  ↓ (6) Web UI で確認
```

各ステップが個別コマンドのため、実行忘れ・順序ミス・エラー見落としが起きやすい。

---

## 提案 STEP 一覧

### STEP 1: ワークフロー統合コマンド（最優先）

**目的**: 毎試合後の決まった手順を1コマンドで実行できるようにする

**内容**:
- `run_all.py`（または `make run`）を追加
- generate → import_db → analytics を順次実行
- 各ステップの成否をわかりやすく表示（OK / NG）
- エラー発生時は途中停止 + 原因を明示

**実装イメージ**:
```bash
python run_all.py [--year 2026] [--skip-analytics]
```

**効果**: 毎回4コマンドを手動実行する手間・ミスがなくなる

---

### STEP 2: データ入力バリデーション強化

**目的**: Excelの入力ミスを DB登録前に検出して警告する

**内容**:
- `validate.py` を追加（generate.py の前に単独実行 or 統合）
- チェック項目:
  - 打席数 vs 打撃内訳の合計不一致（例: 打席3なのに安打2+三振3）
  - 同一試合に同一選手が重複登録されていないか
  - 日付フォーマット異常・対戦相手名の揺れ（スペース有無など）
  - 投手名がチーム単位シートに存在するか
- 警告レベル（WARNING / ERROR）を分けて表示

**効果**: DB登録後に誤データが混入するリスクを事前排除

---

### STEP 3: 実行ログの可視化・履歴確認

**目的**: 「いつ、何を登録したか」を後から確認できるようにする

**内容**:
- 現在 `logs/` 配下にログファイルあり → ログフォーマットを構造化（JSON Lines形式）
- `python show_log.py [--date 2026-03-25] [--step import]` で過去実行履歴を表示
- または Web UI に「実行履歴」タブを追加（/history）
  - 日時・実行ステップ・成功/失敗・対象年度を一覧表示

**効果**: 「今日の試合データを登録したっけ？」が素早く確認できる

---

### STEP 4: DB と Excel の差分チェック機能

**目的**: ExcelとDBがズレていないかを確認できるようにする

**内容**:
- `check_diff.py` を追加
- Excelの打撃成績行数 vs DBのレコード数を比較
- 差分がある場合、どの試合・選手のデータが不足しているかを表示
- `--fix` オプションで差分分のみ再登録

**効果**: 部分的に登録漏れが発生した場合でも素早く特定・修正できる

---

### STEP 5: Web UI からのデータ確認強化

**目的**: ブラウザだけで運用状況をひと目で把握できるようにする

**内容**:
- ダッシュボードに「最終データ更新日時」を表示
- 試合一覧画面で「データ未登録の試合」をハイライト（試合日は記録あるがDB成績なし）
- 選手詳細に「前試合比較」セクション追加（今試合成績 vs シーズン平均）

**効果**: Web UI を開くだけで運用状況が把握できる

---

### STEP 6: Docker Compose による環境統一（中長期）

**目的**: DB起動・アプリ起動を1コマンドに統一し、環境差異を排除する

**内容**:
- `docker-compose.yml` を整備（PostgreSQL + FastAPI バックエンド）
- `docker compose up` でDB + API が一括起動
- 現在 `app_util.py` が担う Docker起動ロジックをcompose管理に移行
- 開発環境セットアップ手順をREADMEに整備

**効果**: 「Dockerが起動してるか」を意識しなくてよくなる

---

### STEP 7: 試合後レポートの自動生成（長期）

**目的**: 試合後に選手・監督へ共有できるレポートを自動生成する

**内容**:
- `analytics.py` の出力をベースに、試合後サマリーを生成
  - その試合の打撃成績一覧
  - ハイライト選手（OPS最高など）
  - シーズン累積成績との比較
- Web UI の印刷用CSS対応（ブラウザ印刷でそのまま使える）
- または PDF出力（reportlab 等）

**効果**: 手動でExcelを整形してコピーする作業が不要になる

---

## 優先順位サマリー

| STEP | 内容 | 優先度 | 工数感 |
|------|------|--------|--------|
| 1 | ワークフロー統合コマンド | 最高 | 小 |
| 2 | データ入力バリデーション | 高 | 中 |
| 3 | 実行ログ可視化 | 中 | 中 |
| 4 | DB↔Excel 差分チェック | 中 | 中 |
| 5 | Web UI 運用状況強化 | 中 | 中 |
| 6 | Docker Compose 整備 | 低 | 中 |
| 7 | 試合後レポート自動生成 | 低 | 大 |

---

## 備考

- STEP 1〜2 は「毎試合後の運用負担軽減」に直結するため最優先
- STEP 3〜5 は「問題発生時の原因特定・確認」を容易にする
- STEP 6〜7 は中長期的な品質向上・共有面の改善
- 各STEPは独立して実施可能（依存関係なし）
